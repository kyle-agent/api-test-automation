## 0. 결론 (headline)

**변경 없음 (zero drift).** 1,372개 엔드포인트 전량을 라이브 문서 사이트에서
재검증했으나 `method` / `http_path` / `title` / `version` / `doc_url` 어느
필드도 구 스냅샷과 다르지 않았다 (`+0 added, -0 removed, ~0 changed, 1372
unchanged`). **재테스트가 필요한 endpoint_key는 0개.**

이는 "리프레시를 안 해서 diff가 0으로 나온" 게 아니라 — 아래 §1 방법론대로
캐시를 강제 우회하고 1,372개 페이지 전부를 개별 재요청해서 얻은 **양성
(positive) 무변경 확인**이다.

## 1. 방법론 (리프레시 성공 여부: 성공)

1. **사전 보존**: 리프레시 전 `data/api_catalog.json`을
   `<scratchpad>/api_catalog_2026-06-05.json`로 백업 (git으로도 복구 가능하지만
   diff 비교용 사본을 별도 보관).
2. **정본 절차 확인**: `docs/agent-team.md` §Spec-Intel, `.claude/agents/spec-intel`,
   `spec/extract_catalog.py` 독스트링을 읽고 canonical 커맨드
   (`python -m spec.extract_catalog` → `python -m spec.summary`) 확인.
3. **캐시 무효화가 필요했음** — 최초 1회 그대로 실행했더니 `discovered 1372
   endpoints; 1372 already in catalog`로 끝나며 파일이 **전혀 안 바뀌었다**
   (`git diff --stat`이 비어 있었음). 원인: (a) `data/.apiref_index.html`이
   2026-06-05/07 커밋 시점에 커밋된 정적 캐시라 `get_index_html()`이 라이브
   fetch 없이 그 캐시를 재사용했고, (b) 기존 카탈로그의 모든 엔트리가 이미
   `method`+`http_path`를 갖고 있어 `enrich()`(개별 페이지 재요청)가 전부
   스킵됐다. 즉 **진짜 라이브 재검증이 0건**이었던 것. 이건 diff 도구의 설계상
   "resumable" 최적화(의도된 동작)이지, 버그는 아님 — 다만 "리프레시"의 의미를
   충족하려면 강제 무효화가 필요했다.
4. **강제 전체 리프레시**: 두 캐시 소스를 모두 삭제 후 재실행 —
   `data/.apiref_index.html` 삭제(인덱스 페이지 강제 재fetch, add/remove/버전
   감지용) + `data/api_catalog.json` 삭제(1,372개 상세 페이지 전부
   `enrich()`로 강제 재fetch, method/path/title/version 시그니처 재검증용).
   `python -m spec.extract_catalog`를 백그라운드로 실행 (~1.4초/페이지 ×
   1,372 ≈ 32분).
5. **중단/재개**: 실행 도중 컨테이너가 재시작되어 백그라운드 프로세스가
   죽었다 (로그 마지막 줄 `progress 500/1372`). `spec.extract_catalog`가
   설계대로 **resumable**함을 확인 — `data/api_catalog.json`에 이미 쓰여 있던
   500개 엔트리(`method`+`http_path` 보유)를 스킵하고 나머지 872개만
   재fetch하며 이어받았다. 재실행 후 정상 완주:
   `done: 1372 endpoints, 1372 with method/path`.
6. **검증**: `python -m spec.summary` → `Unresolved: 0`, 카테고리별 합계는
   `docs/working/CONTEXT.md`에 기재된 기존 수치와 동일 (GET 527 · POST 383 ·
   PUT 244 · DELETE 209 · PATCH 9, 13 categories).
7. **diff**: `python -m spec.diff <old> <new> -v` (+ 필드별 수동 대조 스크립트)
   — 완전 일치.
8. **Bodies/docs 리프레시는 스킵** (오케스트레이터 지시 · 카탈로그 diff가
   0이라 우선순위 낮음): `spec.extract_bodies` / `spec.scrape_docs` 실행하지
   않음 — 시그니처가 안 변했으므로 body 스키마 변경 가능성도 낮다고 판단
   (단, body 자체가 시그니처와 무관하게 바뀔 수 있음을 완전 배제한 건 아님 —
   §5 참고).

## 5. 산출물 / 변경 파일

- `data/api_catalog.json` — 전체 재fetch 후 재작성했지만 **git HEAD와
  바이트 단위로 동일**(`git status`에 안 잡힘). 실질적 워킹트리 변경 없음.
- `data/.apiref_index.html` — 재fetch로 갱신됨, `git diff`상 1줄 변경.
  **내용 변경은 실질적으로 무해한 렌더 아티팩트**: 유일한 차이는 페이지
  템플릿의 언어토글(`한국어`/`English`) 드롭다운 링크의 `href`가 그
  특정 요청이 "현재 보고 있는 페이지"로 간주한 문서 경로 하나를 가리키는
  부분뿐 (구: `ai-ml/cloud-ml/models/cloudmlclustercheckreleasableresponse`,
  신: `ai-ml/aimlops-platform/apis/deleteaimlopsplatformv1/1.1`) — 이건
  캐시 스냅샷을 뜬 시점에 서버가 어떤 상태를 반환했는지에 좌우되는
  비결정적 필드로, `extract_catalog.py`의 파싱 로직(`HREF_RE`/`META_RE`)이
  참조하지 않는 영역이라 카탈로그 내용에 영향 없음. **커밋하지 않음**
  (오케스트레이터 검수 대기, 지시대로).
- `<scratchpad>/api_catalog_2026-06-05.json` — 리프레시 전 백업(구 스냅샷),
  diff의 baseline으로 사용. 리포 밖 scratchpad에 위치, 커밋 대상 아님.
- `docs/working/trackers/SPEC-DIFF-2026-07-09.md` — 본 문서 (신규).
- `data/api_bodies.json`, `data/api_docs.json`, `data/api_catalog_params.json`
  — **미변경** (bodies/docs 리프레시를 스킵했으므로 이 세션에서는 손대지
  않음).

## 6. 주의사항 / 실패 없음

- 문서 사이트 접근은 프록시를 통해 문제없이 이뤄졌다 (`curl` HTTP 200,
  `urllib`도 정상) — 접근 차단/실패 없었음.
- 도구 자체는 정상 동작했으나, **캐시-재사용 설계 때문에 "그냥 재실행"만
  해서는 실제 드리프트를 못 잡는다** — 다음 세션에서도 진짜 재검증을 원하면
  `data/.apiref_index.html` + `data/api_catalog.json`(또는 최소한 그 안의
  `method`/`http_path` 필드)을 지우고 돌려야 한다는 점을 기록해 둔다
  (`.claude/agents/spec-intel`의 mandate #1에 이 캐시-무효화 절차를 명시적으로
  추가하는 게 좋겠다 — platform-improver에게 넘길 후속 아이템으로 제안).
- 세션 중 컨테이너 재시작으로 백그라운드 추출이 500/1,372 지점에서 중단됐다
  가 재실행으로 정상 재개·완주함. 데이터 유실 없음 (resumable 설계가 실제로
  동작함을 확인).
- Bodies(`api_bodies.json`)/full docs(`api_docs.json`)는 **이번 세션에서
  리프레시하지 않았다** (오케스트레이터 지시로 카탈로그 diff 우선, bodies/docs
  는 무리하지 않기로 함). 시그니처(method+path)가 하나도 안 바뀌었으므로
  request body 스키마가 바뀌었을 가능성은 낮다고 보지만, **완전히 배제된 건
  아니다** — 같은 method+path에서 필드만 추가/변경되는 경우는 이번 diff의
  탐지 범위 밖(스크립트가 method/http_path/title/version/doc_url만 추적,
  body 스키마는 추적 안 함). 다음 우선순위로 bodies/docs 리프레시를 원하면
  `python -m spec.extract_bodies` / `python -m spec.scrape_docs`를 (전체
  재실행 시 며칠 걸릴 수 있으므로) `--key-substr`로 스코프를 좁혀 도입하는
  걸 권장.
- **커밋 안 함** — 지시대로 워킹트리에만 남겨둠. `git status --short`는
  현재 `data/.apiref_index.html` 1개 파일만 modified로 표시.
