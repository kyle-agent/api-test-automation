## 1. 무엇을 했고, 왜 표준 파이프라인이 실패했는지

1. **사전 백업**: `data/api_catalog.json`, `api_bodies.json`,
   `api_catalog_params.json`, `spec_diff_latest.json`을 세션 scratchpad에
   백업. 리프레시 전 `spec.summary` 기준선: 1,417 discovered / 1,416
   resolved / 1 unresolved.
2. **`python -m spec.extract_catalog`(기본, resumable)** 실행 →
   `discovered 1417 endpoints; 1417 already in catalog` — 즉
   **전량 cache-hit로 no-op**(모듈 docstring이 명시한 알려진 한계: 기본
   모드는 변경 감지 불가). 카탈로그 파일 바이트 동일 확인(md5 일치).
3. `spec.extract_catalog`의 docstring에 따라 **변경 감지에는 `--fresh`가
   필수**라 재실행 → `data/.apiref_index.html`(2026-08-20 캐시, 5MB)를
   지우고 라이브 index를 새로 받게 함. 결과: **`discovered 1 endpoints;
   0 already in catalog`** — 카탈로그가 1개짜리로 통째로 덮어써짐(source
   of truth 훼손 위험). **즉시 scratchpad 백업으로 원복**하고
   `data/.apiref_index.html`도 `git checkout --`로 커밋 상태 원복(둘 다
   확인 완료, `git status --short data/` 클린).
4. **원인 조사(read-only curl 프로빙, 코드/데이터 변경 없음)**:
   - 라이브 `/apireference/` index 페이지: **31,054 bytes** (2회 재요청
     동일, 결정적/캐싱 아님). href는 13개 카테고리 링크 + 예시 엔드포인트
     1개(`ai-ml/cloud-ml/apis/clusterproduct/1.0`)뿐. 기존 모듈
     docstring이 서술한 "각 상세 페이지가 ~4.3MB, 전체 nav 트리를
     임베드"라는 전제 자체가 더 이상 안 맞음 — **사이트가 nav를 더 이상
     정적 HTML에 전량 임베드하지 않도록 재구성됨**.
   - `/apireference/contents-list/`(RSS `index.xml`이 가리키는 별도
     페이지)는 **카테고리→서비스 레벨**(63개 서비스) 링크를 담고 있음 —
     엔드포인트 레벨은 아님.
   - 서비스 overview 페이지(`/apireference/<cat>/<svc>/`)는 **개별
     엔드포인트 href 목록도 없음**(예: `compute/baremetal/` 페이지에
     `apis/*/​*` 링크 0개) — 대신 사람이 읽는 문서 형태로 `Version` 표
     (CURRENT/SUPPORTED/DEPRECATED)와 **"API Version History"라는
     changelog 섹션**(버전별 `[신규]/[변경]/[삭제]` 또는 영문
     `[New]/[Changed]/[Removed]` 태그 + `<code>METHOD /path</code>`)을
     담고 있음 — 이게 이번 세션이 활용한 대체 신호.
   - **구식 per-endpoint 페이지는 여전히 살아있음**: 카탈로그의 기존
     `doc_url`(예:
     `.../compute/baremetal/apis/listbaremetals/1.2/`)을 직접 재요청하면
     200 + 올바른 `<meta description>`(`get /v1/baremetals ...`)을 반환.
     즉 **카탈로그 자체가 틀린 건 아님** — discovery(신규/삭제 엔드포인트
     찾기)만 깨졌다.
   - 사이트 전역 검색 인덱스(`https://docs.e.samsungsdscloud.com/search-index.json`,
     86MB, minisearch 직렬화 포맷, `documentCount: 35779`)가 존재하긴
     하나 문서 저장소(제목/URL 배열)가 별도 구조라 이번 세션 예산 안에서
     안전하게 역공학하지 못함 — **후속 세션에서 스크레이퍼를 다시
     설계할 때 검토 대상으로 남김**(§6).
5. **대체 방법론 채택**: `data/api_catalog.json`의 63개 서비스(카탈로그
   60개 + `contents-list`에만 있는 4개)에 대해 각 overview 페이지를
   1회씩 GET(총 64 요청, 캐시/재시도 없이 전부 성공) → `Version` 표의
   CURRENT 버전을 카탈로그 보유 최고 버전과 비교 → 다르면 changelog에서
   그 사이 버전의 `[신규]/[변경]/[삭제]` 항목을 정규식으로 추출(태그 +
   HTTP 메서드 + path). 스크립트/원본 페이지는 세션 scratchpad에 보존
   (`svc_pages/*.html`, `svc_version_report.json`,
   `changelog_extract.json`) — 저장소 안에는 아무것도 쓰지 않음.

## 2. 상세 결과

### 2.1 삭제된 서비스 — `networking/cssdlan`
서비스 overview 페이지(`/apireference/networking/cssdlan/`) 자체가
`<title>404 Page not found</title>`. 카탈로그에는 원래 이 서비스의
엔드포인트가 **1개뿐이었고 그마저 `method`/`http_path`가 둘 다 null**
(`networking/cssdlan/setexternalcssdlannetworkchangeinfo`) — 07-09/07-15
리포트가 "nav에는 있는데 페이지가 404"라고 기록했던 바로 그 건이다.
이번에 서비스 페이지 자체가 사라진 걸 확인했으므로 **"nav 오탈자"가
아니라 서비스 전체가 폐기(deprecated/decommissioned)된 것으로 결론**.
카탈로그의 `unresolved: 1`은 이 건 하나이며, 향후 스크레이퍼를 고칠 때
이 서비스를 카탈로그에서 제거하는 게 맞다(이번 세션에서는 안 건드림).
**영향받는 시나리오**: 없음(애초에 method/path가 없어 어떤 lifecycle도
이 엔드포인트를 참조할 수 없었음).

> read-only GET 1회(`docs.e.samsungsdscloud.com` 대상)만 수행했고,

### 7.1 포맷

minisearch 직렬 포맷이 맞다(`serializationVersion: 2`). 최상위 키:
`documentCount`(35779), `nextId`, `documentIds`, `fieldIds`,
`fieldLength`, `averageFieldLength`, `storedFields`, `dirtCount`,
`index`(역색인 트라이, 우리가 쓸 일 없음), `serializationVersion`.

우리가 원하던 "문서 URL/제목이 어디 있나"의 답은 **`storedFields`**
(dict, key는 내부 문서 id 문자열, value는
`{ref, title, body, lang, categories}`)다. `ref`가 URL 경로,
`lang`이 `ko`/`en`, `body`가 **렌더링된 페이지 전체 텍스트**(HTML
태그 제거 후 공백으로 이어붙인 것)다. 예:

```
ref: /apireference/container/ske/apis/createcluster/1.6/
title: "1.6"
lang: "ko"
categories: "Container"
body: "post /v1/clusters Description create a cluster\n상태 ACTIVE (CURRENT)
       ... Parameters ... body body required ClusterCreateRequestV1Dot6
       ... Example HTTP request ... Example HTTP response Response 202 { ... } "
```

**중요한 발견**: `body`는 단순 검색용 요약이 아니라 **method + path +
설명 + 파라미터 표 + 응답 코드 + 실제 예시 request/response JSON까지
전부 평문으로 포함**한다. 즉 이 인덱스 하나로 discovery뿐 아니라
`method`/`http_path`까지(그리고 잠재적으로 스키마 필드 상당 부분까지)
페이지를 다시 fetch하지 않고 뽑아낼 수 있다(§7.4 검증 참고).

사이트 URL 구조는 다음 7종으로 완전히 분해된다(ko 문서 9,758개 =
아래 합계와 정확히 일치):

| 패턴 | 개수(ko) | 내용 |
|---|---:|---|
| `/apireference/` (최상위) | — | 인덱스 자체는 이 세트에 없음(별도 확인) |
| `/apireference/<cat>/` | 14 | 카테고리 페이지 |
| `/apireference/<cat>/<svc>/` | 64 | 서비스 개요 페이지(Version 표 + changelog, §2에서 쓴 것) |
| `/apireference/<cat>/<svc>/apis/` | 63 | "APIs" 목록 페이지 — **body가 빈 문자열**. 클라이언트 사이드 렌더링이라 엔드포인트 href가 정적으로 없음(discovery가 깨진 근본 원인을 여기서도 재확인) |
| `/apireference/<cat>/<svc>/apis/<name>/` | 1,491 | 엔드포인트 이름별 "버전 선택" 페이지 — **역시 body 빈 문자열**, title만 사람이 읽는 요약명(예: `"Accept a volume transfer"`) |
| `/apireference/<cat>/<svc>/apis/<name>/<version>/` | **5,285** | **실제 콘텐츠가 있는 페이지**(카탈로그의 `doc_path`와 같은 구조) |
| `/apireference/<cat>/<svc>/models/` | 63 | 서비스별 스키마 목록 페이지 |
| `/apireference/<cat>/<svc>/models/<Model>/` | 2,778 | 개별 스키마 정의 페이지 |

en(`/en/apireference/...`)에도 동일 구조가 그대로 미러링돼 있다(9,758개,
ko와 1:1 대응) — `apireference` 전체는 19,516개(ko+en), 이번 절의
수치는 전부 **ko만** 집계했다.

이걸로 "왜 서비스 개요/`apis/` 목록 페이지에 엔드포인트 href가
없는가"도 확정됐다: `/apis/`와 `/apis/<name>/` 페이지는 **검색 인덱스
안에서도 body가 비어 있다** — 즉 사이트 자체가 이 두 계층을 순수
클라이언트 사이드 네비게이션(별도 JS 매니페스트, 검색 인덱스에도
안 실림)으로 렌더링한다. 유일하게 전체 목록을 정적으로 얻을 수 있는
경로가 이 minisearch 인덱스의 `/apis/<name>/<version>/` 레벨 항목들이다.

**§2.2 정정**: 지난 세션은 `costnavigator`/`resourceoptimizer`/`cnapp`을

결론지었다. **이건 틀렸다** — 세 서비스 다 실제 엔드포인트 페이지가
살아 있고(resourceoptimizer 24개, costnavigator 3개, cnapp 2개),
직접 라이브 GET으로 재확인했다(`.../resourceoptimizer/apis/getdashboard/1.0/`,
`.../costnavigator/apis/analyzecost/1.0/` 둘 다 **HTTP 200**, 응답
본문이 인덱스의 `body`와 일치). 원인은 지난 세션과 동일한
"discovery 붕괴": 서비스 개요 페이지에는 여전히 이 엔드포인트들로
가는 링크가 없어서 사람이 눈으로 훑어도 못 찾는다 — 이번에 인덱스를
파싱해서야 존재가 드러났다. **결론: 이 3개 서비스는 스텁이 아니라
"카탈로그화 안 된 진짜 커버리지 공백"이다.** `management/cnapp` 쪽은
2개뿐이라 작지만, `resourceoptimizer`는 24개짜리 신규 서비스로
messagehub급 커버리지 기회다.

`networking/cssdlan`(§2.1, 삭제 서비스)는 인덱스 전체(ko+en,
`ref`/`title`/`body` 어디에도) 검색해도 **0건** — "서비스 전체 폐기"
결론이 다시 한번 독립적으로 확인됐다.

### 7.4 method/http_path를 인덱스에서 직접 뽑을 수 있는가 — 검증

`body` 필드의 첫 토큰이 항상 `"<method> <path> Description ..."` 형태다
(정규식 `^(get|post|put|delete|patch)\s+(\S+)`, 대소문자 무관).
5,285개 엔드포인트-버전 행 전부에 대해 이 정규식을 돌린 결과:

- **추출 실패 0건**(5,285/5,285 매치)
- 카탈로그와 `doc_path`가 정확히 겹치는 1,390개 엔트리에 대해
  `method`+`http_path`를 인덱스 추출값과 카탈로그 값을 1:1 비교 —
  **불일치 0건**

즉 인덱스의 `body` 필드만으로 **method/http_path는 100% 신뢰 가능**하다
(적어도 기존에 검증된 1,390개 표본에서는). `body`에는 파라미터 표,
응답 코드, 예시 request/response JSON까지 평문으로 들어있어서
(예: `createcluster` 항목에 `ClusterCreateRequestV1Dot6` 스키마명과
`kubernetes_version`, `vpc_id` 등 실제 필드가 들어간 예시 JSON까지
그대로 보임) `spec.extract_bodies`가 지금 페이지별로 하는 일의 상당
부분도 이 한 파일에서 끝낼 수 있어 보인다 — 다만 필드 단위 타입/enum
제약까지 스키마 표를 파싱해서 재구성하는 건 이번 세션에서 깊게
검증하지 않았다(파라미터 표 파싱 프로토타입은 스코프 아웃, 후속
과제로 남김).

### 7.5 실행 가능성 평가 및 `spec/extract_catalog.py` 구현안

**결론: 실행 가능 (Go).** discovery 단계를 다음으로 교체할 것을 제안한다
(코드는 이번 세션에서 건드리지 않음 — 아래는 제안일 뿐):

1. `search-index.json`을 기존 index.html 캐시(`data/.apiref_index.html`)와
   같은 패턴으로 캐시(`data/.search_index.json`), `--fresh`로만
   재다운로드. 기존 모듈의 503 재시도 래퍼를 그대로 재사용.
2. `storedFields`를 순회하며 `lang == "ko"`이고
   `ref`가 `^/apireference/([^/]+)/([^/]+)/apis/([^/]+)/([^/]+)/?$`에
   매치하는 것만 채택 — 이게 오늘 index.html href 정규식이 하던 일을
   그대로 대체한다.
3. `(category, service, name)`별로 인덱스에 존재하는 모든 버전 중
   `max()`를 "현재 버전"으로 채택(카탈로그가 이미 엔드포인트당 버전
   1개만 추적하는 것과 동일 정책). **단, §7.2에서 확인했듯 인덱스가
   과거 버전을 얼마나 보존하는지는 서비스마다 다르므로("최신 버전만
   결정적으로 신뢰, 과거 버전 존재 여부는 신뢰하지 말 것"이 안전한
   원칙)**.
4. `method`/`http_path`는 `body` 필드 첫 줄 정규식으로 채우고(§7.4
   검증 완료), 상세 스키마/파라미터는 지금처럼 라이브 페이지를
   추가로 fetch(또는 향후 `body` 파싱을 더 정교화).
5. **가드레일**: 새 discovery 결과 개수가 기존 카탈로그의 90% 미만이면
   (이번 `--fresh` HTML crawl이 "발견 1개"로 카탈로그를 날려먹었던
   사고처럼) 쓰기를 거부하고 사람이 확인하게 함 — 지금 인덱스 기준
   `(cat,svc,name)` 유니크 카운트는 1,491개로 카탈로그 1,417개보다
   **많다**(정상 범위).
6. 이 경로는 discovery뿐 아니라 §7.3에서 낸 "881개 버전 드리프트 +
   75개 완전 신규" 같은 diff 산출까지 **한 번의 86MB 다운로드로
   부수적으로 얻어진다** — 서비스별 changelog 페이지를 63번 GET하던
   §2의 대체 방법론보다 훨씬 싸고 훨씬 정밀하다.

**주의할 점(gotcha)**:
- **staleness**: `search-index.json`은 사이트 빌드 산출물이라 라이브
  페이지보다 몇 분~몇 시간 뒤처질 수 있다(이번 세션엔 직접 검증할
  방법이 없었음 — 라이브 재확인 curl 몇 건은 전부 인덱스와 일치했다).
  중요한 delta는 인덱스로 스크리닝한 뒤 라이브 GET으로 표본 검증하는
  2단계를 권장.
- **과거 버전 보존 불일치**: `container/ske`/`compute/virtualserver`류는
  전체 버전 히스토리가 인덱스에 다 있는데
  `storage/archivestorage`류는 최신 버전만 남아있다(구버전 페이지는
  라이브엔 여전히 200인데 인덱스에서만 빠짐, §7.2). "인덱스에 없다 ==
  페이지가 죽었다"로 해석하면 안 됨.
- `/apis/`, `/apis/<name>/` 두 계층은 인덱스에서도 body가 비어 있어서
  discovery에 못 쓴다 — 반드시 `/apis/<name>/<version>/` 레벨(리프
  노드)만 걸러야 한다.
- 86MB 파일 하나를 통째로 `json.load`해야 해서(스트리밍 파서 없이) 최소
  수백 MB 메모리가 필요하다(이번 세션 환경에서 실측 피크 메모리는
  별도로 안 쟀지만 파싱 자체는 1.7초, 문제 없었음) — CI 러너 메모리
  제약이 있다면 확인 필요.

### 7.6 프로토타입 실행 시간

스크래치패드에 독립 스크립트(`prototype_discover.py`, 저장소에는 없음,
`spec/*.py` 미수정)로 "다운로드 → JSON 파싱 → `/apireference/`
엔드포인트-버전 행 필터링 → method/path 정규식 추출"을 콜드 스타트로
1회 실행:

| 단계 | 소요 시간 |
|---|---:|
| 다운로드(86MB, 프록시 경유) | 7.00초 |
| `json.load` 파싱 | 1.75초 |
| 필터링 + method/path 정규식 추출(5,285건) | 0.02초 |
| **합계** | **8.77초** |

기존 `spec.extract_catalog`가 (모듈 docstring 기준) 엔드포인트당
페이지 1개씩(~1,400개, 페이지당 최대 4.3MB로 서술돼 있었음) 순차
fetch하던 것과 비교하면, discovery + method/path 채우기까지 **10초
이내로 끝나는 대체 경로**다.
