# V2 실행 방식 실험 로그

> 오너 위임(2026-07-09): PM(이 세션)이 역할 분담·병렬 폭·에이전트 수·모델
> 배분을 전권으로 결정하고, 방식의 유효성을 기록해 포스트모템의 원료로 남긴다.

## 체제

- PM/아키텍트: 메인 세션(Fable) — 계약·설계·통합·게이트 판단
- 실측 조사원 / 구현 개발자 / 페르소나 검수자(P1·P2·P3) / 코드 리뷰어: 서브에이전트
- 오너 게이트 3개: G1(계약+셸+상황실 방향 확인) · G2(서비스 상세 데모) · G3(네비 전환 직전)
- 검수 동선: 평시 Playwright 스크린샷 → 게이트 시 클릭 가능한 미리보기 → 최종 인수는 오너 로컬 실물

## 기록 양식 (화면/단계별)

| 필드 | 내용 |
|---|---|
| 단계 | 무엇을 만들었나 |
| 방식 | 단독 / 파이프라인 분업 / 병렬 N |
| 모델 배분 | 역할별 |
| 에이전트 수 | |
| 결과 | 소요(체감)·리워크 횟수·에이전트 선발견 결함 수·오너 수정 요청 수 |
| 교훈 | 다음 단계에 반영할 것 |

## 로그

### E0 — 정찰 (M0 준비) · 2026-07-09
- 방식: **읽기 전용 정찰 4 병렬** (발행물 구조 / 컨트롤플레인 배선 / 로컬 런·fold / 서비스 상세 원천)
- 모델: 정찰 = Sonnet (기계적 탐색), 합성·계약 작성 = PM(Fable)
- 가설: L1 계약의 병목은 "쓰기"가 아니라 "실측"이므로 실측을 병렬화하면 계약 리드타임이 크게 준다.
- 결과: **성공.** 4건 병렬 ~2~4분 내 전부 회수(각 8만~11만 토큰, 도구 17~51회).
  계약 작성에 필요한 결정적 사실 4개를 선발견 — (1) 발행 시각/식별자가 흩어져
  있어 정본 규칙 필요, (2) dashboard.build가 순수 함수라 import 재사용 가능
  (HTML 파싱·로직 복제 회피), (3) 로컬 Observation.run이 빈 문자열 → 시간창
  근사 한계, (4) fold(main)≠publish(dashboard-data) 구분. 이 중 (2)(3)은
  PM이 단독 탐색했으면 놓치기 쉬웠던 것으로 판단.
- 교훈: 읽기 정찰은 Sonnet 병렬로 충분히 정확. 단, 결과 보고가 길어 PM 컨텍스트
  소모 큼 — 다음부터 보고 형식에 "표+결론 N줄" 상한을 명시할 것.

### E1 — M0 계약 + M1 셸 + M2 상황실 (G1 구간) · 2026-07-10
- 방식: **PM 단독 제작** (공용 장치의 품질이 전체를 좌우한다는 판단 —
  용어상수·배지 매크로·발행 메타 로더는 위임하지 않음)
- 결과: 정찰 완료 후 계약+셸+상황실+테스트까지 한 호흡. offline 테스트
  6종 신설 + 기존 21종 무손상. 셀프체크(스크린샷 육안 검토)에서 결함 1건
  선발견·수정 — KPI 짝 오류(tested/total이 검증(C3) 카드에 오배치).
  스택 특이점 1건: Starlette 신버전 TemplateResponse(request, name, ctx)
  시그니처 — 기존 코드 관례를 확인해 해결.
- 교훈: (1) "스크린샷 셀프체크"는 코드 리뷰가 못 잡는 의미 결함(짝 오류)을
  잡았다 — 파이프라인 표준 단계로 유지. (2) 다음 단계(서비스 상세)는 구현
  위임 + 페르소나 검수 실험을 걸 것 (E2로 기록 예정).

### E2 — 서비스 축: 구현 위임 + 페르소나 검수 3인 · 2026-07-10
- 방식: **구현 = Sonnet 개발자 에이전트 1인 위임**(계약·경계·보고 형식을 명시한
  스펙 프롬프트) → **검수 = 페르소나 3인 병렬**(P1 신규/P2 운영자/P3 임원,
  스크린샷+라이브 HTML 실사용) → PM 통합 수정.
- 구현 결과: 목록+상세+404+데이터층+테스트 3종을 1사이클에 완성(약 12분,
  16.4만 토큰). 계약 이탈 판단 5건을 근거와 함께 보고 — 전부 타당해 수용.
  경계(controlplane/v2/**만 쓰기) 위반 0. 중간 규칙 변경(문구 격식화)을
  SendMessage로 전파하니 실시간 반영됨.
- 검수 결과: 3인이 **상 2건 포함 결함 17건**을 오너 검수 전에 발견. 최대
  수확은 P3의 "검증 72% > 호출 56% 논리 충돌" — 원인은 PM이 발행 필드
  의미(cov_op/tested)를 기억으로 라벨링한 것(Hard Rule 5 위반 사례).
  build.py 실측으로 교정(호출(C2)=tested/total=94.4%). P2는 "새 회귀→상세"
  동선 단절을, P1은 CTA 무예고 낙하를 잡음 — 관점 분산이 실제로 서로 다른
  결함군을 냈다.
- 교훈: (1) 위임 구현은 스펙+경계+보고형식이 명확하면 품질 손실 없이 동작 —
  표준으로 채택. (2) 페르소나 검수는 비용 대비 효과가 커서(3인 병렬 ~2분)
  화면마다 상시 편성. (3) 수치 라벨은 반드시 산출 코드 실측 후 부착 —
  계약 문서에도 필드 정의 출처(파일:라인)를 남길 것.

### E3 — 결과 축: 정찰→계약 보강→위임 구현 · 2026-07-10
- 방식: E2 표준 파이프라인. 단 페르소나 검수는 이번 라운드 **의도적 생략** —
  화면의 핵심 동적 케이스(실제 회귀 목록)가 현재 발행본에서 재현 불가
  (최신 발행 healthy)라 fixture 테스트로 대체했고, 실제 회귀가 발행되는
  시점에 P2 재검수를 예약.
- 수확: (1) 정찰이 fail_new 2건의 실체(동일 호출의 이중 기록·transient
  500→201 자연복구)와 발행본에 fail 상세 전용 파일이 없다는 갭을 확정 —
  임시 우회(배너 파싱)를 계약에 명시하고 정공법은 엔진 요청 #1로. (2) 구현
  에이전트가 Hard Rule 5를 자발 적용해 발행본 재실측 → **발행 산출물 간
  판정 불일치**(07-09 발행 healthy vs history 07-07 fail_new=2)를 발견.
  PM이 판정 배지를 판정 시각(history ts)으로 분리해 방어 + 엔진 요청 #4.
- 교훈: 위임 에이전트에게 "실측 참고"를 줄 때도 재검증 지시가 유효 —
  이번 발견은 프롬프트의 예시를 맹신하지 않은 데서 나왔다.

### E4 — D7 개정 일괄 적용 + Runs 축 v1 · 2026-07-10
- D7 개정(이름 영어/설명 한국어): 라벨 매핑표 ~50항목을 프롬프트에 박아
  위임 → 드리프트 0, 매핑 외 판단 7건 전부 규칙 부합. **용어 상수 모듈
  덕에 정책 반전 비용이 낮았다** — 초기 설계 투자의 회수 사례.
- Runs 축 v1: 안전이 핵심이라 계약(§2.6)에 "발사 없음·게이트 하드코딩
  금지·read-only=열람 모드"를 명문화하고 위임. 에이전트가 실효 게이트의
  올바른 원천(core.config.settings — HTTP 클라이언트가 집행하는 싱글턴)을
  코드 추적으로 특정해 근거와 함께 보고 — 검증 수월.
- 교훈: 안전 관련 화면은 "무엇을 하지 말라"를 계약에 명시하는 것이
  가장 효과적인 가드레일이었다.
