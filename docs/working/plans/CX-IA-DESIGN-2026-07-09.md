## 1. 요약 (1페이지)

### 3줄 진단

1. **개별 화면의 완성도는 높은데, 화면 사이의 "진실"이 서로 싸운다.**
   같은 시각에 홈은 "신규 fail 2건"(빨강), Reporting > 대시보드 탭은 "HEALTHY ·
   새 회귀 0건 · 배포 안전"(초록), 색칠지도는 "0 tested"를 표시했다 — 세 출처
   (07-07 스냅샷 / 07-09 발행본 / 로컬 관측)가 탭 하나 차이로 병렬 노출되는데,
   어느 값을 믿어야 하는지 중재하는 장치가 없다.
2. **가장 좋은 답이 가장 깊은 곳에 있다.** 페르소나 과업의 정답 화면(서비스별
   엔드포인트 상태표, 잔존 자원, 실패 상세)은 존재하지만 발행 대시보드 하위
   3~5홉 지점이나 콘솔 ②단계 내부에 묻혀 있고, 컨트롤플레인 네비·검색 어디서도
   직접 도달할 수 없다.
3. **내부 은어가 1급 UI 언어다.** C1/C2/C3, cov_op, M3 §4-A1·A2·A3, R2c,
   composer.graph_view, ANTHROPIC_API_KEY 미설정 같은 코드네임·env변수·모듈명이
   화면 제목과 에러 문구에 그대로 노출되어, 문서를 안 읽은 사람은 첫 화면에서
   언어 장벽에 부딪힌다.

### 제안 방향 (한 문단)

IA의 뼈대(Modeling → Testing → Reporting 파이프라인)는 유효하므로 갈아엎지
않는다. 대신 (1) **모든 수치에 출처·시점 배지를 강제**하는 데이터 표시 원칙을
도입해 "세 가지 진실" 문제를 끝내고, (2) **서비스 상세를 1급 시민으로 승격**해
"특정 서비스가 지금 어떤가"라는 최빈 질문에 2클릭 안에 답하게 하고, (3) 흩어진
런 이력(3곳)·잔존 뷰(3곳)·그래프(3곳)를 각각 하나의 표면으로 접합한다. 구조
개편은 legacy 콘솔이 이미 증명한 "**같은 그래프, 오버레이만 교체**" 원칙을
이식하는 B안(재구조화)을 최종 형태로 삼되, 이번 주는 A안(점진 개선)의 quick
win부터 진행하는 2단계 접근을 권고한다.

### 강점 (지킬 것)

1. **파이프라인 멘탈모델**: Modeling → Testing → Reporting 축과 홈의 3단계
   카드는 신규자도 5초 안에 흡수한다. 버릴 이유 없음.
2. **콘솔 ①단계의 계획 UX**: 선택 → 의존 자동 포함 DAG → 견적(스텝 수·quota·
   과금) → pre-flight의 단계적 정보 공개는 이 도메인에 정확히 맞는 패턴.
   과금 체크박스로 실행 버튼을 잠그는 것도 모범적.
3. **작업 큐(worklist)**: "왜 필요한가" 열, 계정 게이트 제외 후 "할 일 73"으로
   좁혀 주는 과업 지향 설계 — 이 패턴을 다른 화면으로 수출해야 한다.
4. **발행 서비스 상세 페이지**: 엔드포인트별 최근 상태·응답시간·다음 작업
   후보까지, P1 과업의 완결적 답. 문제는 품질이 아니라 **배치**(깊이 4홉+).
5. **카탈로그 검색**: method·path·service 즉시 필터는 빠르고 정확.
6. **맥락 배지의 존재 자체**: SNAPSHOT/LIVE/노후 스트립, Testing에서 문구가
   "실행·자원 수치는 라이브 — 커버리지 수치만 스냅샷"으로 바뀌는 디테일 —
   방향은 옳고, 적용이 불완전할 뿐.

### 약점 (구조적)

**W1. 진실의 원천 3개가 무중재 동거** — 로컬 관측(reports/results/*.jsonl),
고정 스냅샷(sha 1114500, 07-07), 최신 발행본(07-09)이 화면·탭 단위로 섞인다.

거리. 사용자가 세 출처의 존재를 스스로 역공학해야 한다. 빈 로컬 DB에서 0을
"사실"처럼 렌더하는 empty-state 부재가 이 문제를 최악으로 만든다(P1-4).

**W2. 같은 질문에 답하는 표면이 3~4개씩** —
- 런 이력: 홈 최근 RUN · Reporting 실행 기록(라이브+아카이브) · ops.html 런 이력
  (+ 콘솔 ② 실행 기록) — 4곳 모두 서로 다른 부분집합.

- 대형 그래프: 색칠지도(커버리지색) · Modeling 의존그래프(provenance색) · 콘솔

**W3. 네비의 이중 정부** — 컨트롤플레인 톱네비(7항목)와 발행 대시보드의 내부
네비(Platform 콘솔·Knowledge·Ops·legacy 콘솔)가 따로 논다. 런 상세 → 스냅샷
대시보드로 들어가면 톱네비가 소멸하고 다른 세계의 네비가 나타난다(P2-5).
ops.html처럼 컨트롤플레인 네비에 없는 화면은 대시보드를 경유해야만 존재를
알 수 있다.

**W4. 톱레벨 7항목 중 2개가 자기 정체성 문제** — 카탈로그는 스스로 "통합됨·
참조용"이라 말하고(그럼 왜 1급 메뉴인가 — P2C-14로 "유틸 링크 강등"은 이미
됐지만 새 사용자 눈에는 여전히 톱바의 동급 항목으로 읽힘), 대시보드는 클릭하면
다른 셸로 이동(외부 이동 표시 없음). AI·Knowledge는 에이전트 내부 도구 성격인데
사용자 동선(파이프라인)과 동급으로 배치.

**W5. 용어 체계 부재** — 세 층위가 무정의로 혼용된다:
(a) 도메인 등급 코드 C1/C2/C3, cov_op/cov_get, soft 4xx, known-red;
(b) 내부 계획 코드네임 M3 §4-A1·A2·A3, R2c, §1 스키마, C4/C5, RESOURCE-MODEL-PLAN 경로 2;
(c) 구현 식별자 composer.graph_view, /api/capacity, oplog, loggingaudit,
ANTHROPIC_API_KEY, APITEST_PLATFORM_URL, PLATFORM_GITHUB_TOKEN.
(a)는 정의 툴팁이 없고, (b)(c)는 화면에 있을 이유 자체가 없다. 한/영 혼용도
불규칙(색칠지도·잔존·트리아지 vs Test Planning·VALIDATED·known-red).

**W6. 실시간 vs 스냅샷의 시각 언어 없음** — 어떤 숫자는 15초 폴링(홈 RUN),
어떤 것은 2일 전 고정(KPI), 어떤 것은 페이지를 열어야 수집 시작(런타임 뷰
30~90초 백지). 같은 타이포·같은 카드 스타일이라 구분 불가. 안전 표시조차
정적 문자열일 수 있음이 확인됨(pre-flight 칩 하드코딩 — console2.js:1602).

**W7. 진입점 혼란** — "어제 뭐가 깨졌지?"라는 최빈 질문의 시작점이 홈 알림 →
트리아지(카운트뿐) → 실행 기록(비어 있음) → 아카이브 런 상세(기록 없음) →
스냅샷 대시보드(다른 셸)로 5단계 순환하며, 어디에서도 fail 목록을 만나지
못한다(P2-3~5). 질문에서 답까지의 경로가 설계되어 있지 않고, 표면들을 이어
붙인 흔적만 있다.

## 4. 디자인 안 (핵심)

### 4.0 두 가지 횡단 원칙 (A안·B안 공통 전제)

**원칙 1 — 라이브 데이터 표시 규약**
1. 모든 수치 카드·표·배너에 **출처 배지**를 강제한다. 3종만 허용:
   - `지금 이 서버`(초록 점, 폴링 주기 명시) — 콘솔 대기열, 진행 중 런, 잔존
   - `발행 @sha·시각`(파랑) — 커버리지, 회귀, 정합성 등 공식 수치
   - `이 런 @run-id`(보라) — 런 상세·런 스냅샷 화면의 모든 값
2. **한 화면(카드)의 기본값은 한 출처.** 두 출처를 견줄 때는 "발행 74.4% ·
   로컬 관측 없음"처럼 명시적 짝으로만 병기한다. 지금처럼 정합성 패널 하나에
   발행 900/454/18과 로컬 0/0/0을 무설명 병렬하는 것(§2 P1-4)을 금지.
3. **empty-state는 0과 다르다.** 로컬 관측이 없으면 "0 ok"가 아니라 "이 서버
   에서 실행된 런 없음 — 공식 수치는 발행 대시보드 참조 →"를 렌더한다.
4. **노후 규칙**: 발행본이 24h 이상 묵으면 배지 노랑 + 값 옆 회색화(지금은
   "노후" 칩만 있고 값은 생생한 검정 — 눈은 값만 읽는다).
5. **헤드라인 단일화**: 회귀 유무 같은 판정성 헤드라인(빨강/초록 배너)은 전
   앱에서 **한 출처(최신 발행본)만** 사용. 스냅샷 고정 화면에서는 판정 배너를
   재계산하지 말고 "이 스냅샷 당시: fail 2"로 과거형 표기.

**원칙 2 — 용어 규약**
1. 1급 화면 용어는 한국어: 검증됨(C3)·호출됨(C2)·도달가능(C1)·잔존·과금처럼
   **한국어 우선 + 코드 괄호 보조**. C1/C2/C3 첫 등장 요소에는 정의 툴팁
   (한 줄: "검증(C3) = 실제 2xx로 동작 확인").
2. 내부 코드네임(M3 §4, R2c, §1, C4/C5, RESOURCE-MODEL-PLAN)·모듈명
   (composer.graph_view)·API 경로(/api/capacity)·env명(ANTHROPIC_API_KEY 등)은
   화면 문구에서 제거. env 미설정 에러는 "AI 분석이 꺼져 있습니다 — 관리자
   설정 필요(도움말)"로 순화하고 기술 상세는 접기/툴팁으로.
3. "상태" 3의미의 어휘 분리: **모델 상태**(모델됨/검증됨), **런 결과**
   (성공/실패/스킵), **커버리지**(%). 라벨에 "상태" 단독 사용 금지.
4. 제품명 단일화: 모든 셸 헤더 "SCP API Regression" 하나로(콘솔의 "Platform"

| Reporting > 색칠지도 | (1) 지도 상단에 **검색→포커스** 입력(카탈로그 검색과 동일 UX). (2) 그룹 펼침 시 해당 그룹으로 줌·팬. (3) ①회귀 패널에 empty-state 규칙 적용(원칙 1-3) |
| Reporting > 실행 기록 | 라이브/아카이브 2섹션을 병합 타임라인으로. 각 행에 "결과 요약(ok/fail/스킵)" 인라인 — 런 상세에 들어가기 전에 판단 가능하게 |
| 런 상세 /runs/{id} | (1) 외부 런이라도 스냅샷에서 결과 요약·fail 목록을 **이 페이지에** 렌더(대시보드 점프 강요 제거). (2) 스냅샷 대시보드로 갈 때는 상단 컨트롤플레인 네비를 유지한 채 임베드 or "↗ 별도 셸" 명시. (3) env 에러 문구 순화(원칙 2-2) |
| Testing 콘솔 | (1) pre-flight 게이트 칩을 실효 상태 바인딩(READ-ONLY 강제 시 "mutations OFF — 이 런은 기록만" 표시). (2) "대기열 추가" 시 토스트+단계 전환 애니메이션. (3) ETA를 "이 조합 순차 실행 시 ~39분 → 병렬로 ~2–3분"처럼 문장화. (4) resource model 죽은 링크 수리, "대시보드" 라벨을 "홈"으로. (5) 상태바 "LIVE" 칩에 툴팁("실행 시 실제 클라우드에 작용") 또는 "실행모드: LIVE"로 라벨링 |
| 잔존/자원 | 런타임 뷰를 잔존의 단일 표면으로 지정: (1) 열 때 자동 수집 대신 **마지막 수집 결과 캐시 + "새로 수집(30~90초)" 버튼**. (2) 콘솔 ② 잔존 줄과 ops.html 자원 섹션은 이 뷰로 링크. (3) 홈 KPI 4번째 칸에 "잔존 자원 N (마지막 확인 hh:mm)" 노출(D8) |
| 카탈로그 | `/catalog`를 Modeling 하위 탭 "인벤토리"로 이동(기존 URL 리다이렉트). 자기부정 배너 제거. 외부 문서 링크에 ↗ 아이콘 |
| Reporting > 대시보드 탭 | 임베드 상단에 "이 수치는 최신 발행본(07-09) — 헤더 스냅샷(07-07)과 다를 수 있음" 한 줄(스트립 약속 위반 해소) — 장기적으로는 D2로 근본 해결 |
| AI | 제목을 "AI 도구 — 초안 생성·영향 분석"으로, A1/A2/A3/R2c 대신 기능명("스펙 변경 영향 분석", "시나리오 초안", "사실 추출", "자원 모델 초안"). 코드네임은 카드 각주로 |
| 딥링크 | `?tab=` 파라미터를 전 탭에서 지원(compare 포함)하거나 경로 방식으로 통일 |

### 4.2 B안 — 재구조화 (질문 중심 IA + 그래프 단일화)

A안이 표면을 정리한 뒤의 목표 상태. 핵심 아이디어 2개:
(i) 네비를 "무엇을 하나"(행위)에서 **"무엇이 궁금한가"(질문)**로 재편,
(ii) legacy 콘솔이 증명한 **"같은 그래프, 오버레이만 교체"**(관찰: legacy는
Catalog→Plan→Run→Report 4단계가 그래프 하나를 공유하고 오버레이만 바꿈 +
우측 노드 인스펙터)를 이식해 그래프 3개를 1개로 접합.

> 참고: 이 방향은 신규 제안이 아니라 내부에 이미 선언된 노스스타의 실행이다 —
> *"One object, three lives. The composition DAG is the same artifact across
> plan / live-run / coverage — colored by intent while picking, by progress
> while running, by coverage while analyzing."* (console2-ia-ux-review.md:113,
> poc/scenario-viz PLATFORM-PLAN 계보는 오너 2026-06-15 결정). 제3자 실사용
> 관찰이 같은 결론에 독립적으로 도달했다는 점이 이번 리뷰의 기여다.

```
[SCP API Regression]                                  ⌕ 전역 검색(서비스·엔드포인트·run)
│
├ ① 상황실 (홈) — "지금 어떤가?"
│   헤드라인(발행본 단일) · KPI(출처 배지) · 병합 런 타임라인 · 잔존 요약 · 다음 우선순위
│
├ ② 서비스 — "이 서비스는 어떤가?"  ★신설, 1급 시민
│   서비스 목록(검색·정렬: 커버리지↓·회귀·게이트) 
│   └ 서비스 상세(발행 services/*.html의 네이티브화):
│      개요(검증 n/m·읽기/쓰기%·결함) | 엔드포인트 표(최근 상태·응답시간)
│      | 모델(노드·의존 미니그래프=인스펙터) | 실행 이력 | [▶ 이 서비스 실행] 딥링크
│
├ ③ 모델 — "테스트를 어떻게 정의했나?" (현 Modeling)
│   모델 표 · 작업 큐 · 노드 에디터 · 인벤토리(구 카탈로그)
│   ※ 독립 의존그래프 탭 없음 — 의존은 서비스 상세·노드 에디터의 인스펙터로
│
├ ④ 실행 — "돌리자" (현 Testing)
│   계획(선택→DAG→견적) → 실행·모니터(대기열·용량·잔존·흐름) → 기록
│   원격(CI 디스패치·스케줄)은 같은 화면의 "실행 위치" 선택지로 통합(D5)
│
├ ⑤ 결과 — "무엇이 나왔나?" (현 Reporting 재편)
│   요약(사다리+스냅샷) · 회귀·트리아지(fail 상세 포함) · 런 타임라인(단일)
│   · 런 상세(결과·트리아지·잔존·스냅샷 대시보드 임베드) · 비교 · 색칠지도
│
└ 도구 ▾  AI 초안 · Knowledge · 발행 대시보드 ↗ · Ops ↗ (legacy 콘솔은 이식 완료 후 제거)
```

그래프 단일화 스펙: `resource_graph.js` 렌더러 하나에 오버레이 4종 —
`인벤토리`(모델됨/미모델) · `모델`(VALIDATED/docs/불완전) · `커버리지`
(검증/도달/미관측) · `계획`(생성 순서·선택 강조). 어디서 열든 동일한 조작
(검색→포커스, 그룹 펼침=줌, 노드 클릭=우측 인스펙터), 오버레이 스위처만 다름.
→ 학습 1회로 3화면 흡수, "같은 그림 다른 의미" 문제 소멸.

서비스 상세가 생기면: P1 여정 6화면 → 2클릭(전역 검색 "loadbalancer" → 서비스
상세), P2 실패 파기 5홉 → 2홉(홈 배너 → 트리아지 상세 → 해당 서비스), P3는
상황실 헤드라인 하나로 3분 목표 달성.

### B. 이번 관찰과 기존 백로그의 관계 요약

- 기존 트래커(P1/P2 계열 19건 + P2C 23건)는 **화면 단위 결함**을 거의 다

  P2C-18~22(실행 뷰), P2C-14(네비 3단계)의 효과가 체감됐다.
- 이번 리뷰의 기여는 화면 단위가 아니라 **화면 사이**에 있다: 출처 3원화(W1),

  건드린 영역이며, 남은 open 항목(P3-13 용어, P3-14 테마, Q8~B7 콘솔 백로그)도
  이 구조 문제의 증상들이다.
- 따라서 권고 우선순위는 "새 결함 수리"가 아니라 §4.0의 두 원칙(출처 배지·용어
  규약)을 시스템으로 도입하는 것이며, 이는 기존 open 항목 다수(P3-13, Q6-잔여,
  B5, P2-9 잔여)를 한 프레임으로 흡수한다.
