### 1.3 "932개 변경"의 실제 의미 — 표본 검증

카탈로그 시그니처 diff가 잡은 932개 필드 변경은 전부 `{title, version, doc_url}`
세 필드뿐(= 문서 페이지의 버전 태그가 올랐다는 뜻; 이 스키마에서 `title`은
API 이름이 아니라 페이지 버전 문자열 그 자체라 `version`과 사실상 동일 신호).
**`method`/`http_path` 변경은 0건** — 라우트 자체가 바뀐 곳은 없다.

표본 검증: `compute/baremetal/listbaremetals` (GET, 1.1→1.2, 932건 중 하나,
바디 스키마 매칭 대상 아님)을 라이브 재요청 → 쿼리 파라미터 목록
(`size,page,sort,server_name,state,ip,vpc_id`)이 구 스냅샷과 **완전히 동일**.
즉 이 엔드포인트는 페이지 버전만 올랐지 계약(contract)은 안 바뀐 것으로
보인다 — 아마 같은 서비스의 write 엔드포인트가 바뀌면서 서비스 전체 문서
번들이 함께 재배포된 부수효과로 추정(가설, 미검증). **따라서 "932개가 전부
API 변경"이라고 읽으면 과대추정**이다. 이번 세션은 write(POST/PUT/PATCH)
바디 스키마 변경만 정밀 검증했고(§1.4), GET 전용/응답 스키마만 바뀌었을
가능성은 스코프 밖(§8 미해결 질문).

## 6. 미해결 질문 / 후속 권장 사항

1. **932개 시그니처 변경 중 미검증 892개**: 이번 세션은 write 엔드포인트의
   요청 바디 스키마 변경(40개)만 정밀 검증했다. 892개는 (a) 순수 페이지
   버전 노이즈(§1.3 표본 검증 근거)일 가능성이 높지만, (b) GET 응답 스키마나
   쿼리 파라미터가 조용히 바뀐 케이스가 섞여 있을 가능성을 완전히 배제하지
   못한다. 후속: conformance 축(정적 분석)이나 여유 있는 spec-intel 세션에서
   `spec.scrape_docs --only endpoints`를 write 외 다른 서비스로 확대해
   샘플링 늘리는 것을 권장.
2. **필드 델타 없이 페이지만 새 버전인 3건** (`aimlops-platform/
   releaseaimlopsplatformv1`, `baremetal/createbaremetals`,
   `multinodegpucluster/creategpunodes`) — 내 정규식 휴리스틱이
   `required`/`optional` 텍스트 인접 매칭이라 필드명이 문장 중간에 끼거나
   테이블 렌더링이 다르면 놓칠 수 있다. `spec.scrape_docs`의 정식
   `parse_model()`(TableExtractor 기반)으로 재확인 권장(이번엔 시간상
   40개 중 이 3개는 정식 파서로 재확인 못 함 — 나머지 37개는 §5에서 이미
   정식 파서로 병합함).
3. **KMS `createkey`의 `acl_cidr`/`private_acl_enabled` 실제 검증 형식** —
   secretsmanager 쪽 동일 필드가 "acl_cidr는 /25 이상이어야 함"(2026-06-23
   검증 기록, `knowledge/validated-facts.md`)이었다. KMS도 같은 제약일
   가능성이 높으나 옵션 필드라 당장 breaking은 아니므로 이번엔 미검증.
4. **45개 신규 엔드포인트의 bodies/docs**: 카탈로그 시그니처(method/path)만
   확보했고, 신규 엔드포인트 자체의 상세 문서(요청 바디 스키마 등)는 아직
   `data/api_docs.json`/`api_bodies.json`에 반영 안 함(Address Group 8개,
   SQL Server DR 5개, servicewatch 6개 등). 커버리지를 새로 작성할 담당
   에이전트가 있다면 그 전에 해당 서비스만 좁혀
   `spec.scrape_docs --key-substr <service>` / `spec.extract_bodies
   --key-substr <service>`로 채우는 것을 권장.
5. **`networking/cssdlan/setexternalcssdlannetworkchangeinfo` 404**: 문서
   사이트 자체의 nav-vs-page 불일치로 보인다(3회 재확인 동일). 플랫폼팀 보고
   대상일 수 있으나 우리 쪽 조치 범위 밖 — `spec.summary`의
   "unresolved=0" 가드레일이 이번엔 1로 나온다는 점만 인지 필요(catalog는
   여전히 나머지 1,415개 전부 해석됨, 전체 신뢰도에 영향 없음).
