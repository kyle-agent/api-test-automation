# owner 계획 (2026-06-13): "과금 없는 자원 하나 만들고 tag 붙이고 떼고" —
# resource-group 자체가 그 자원이다 (zero-cost + 생성 응답에 srn).
# SRN 태그 패밀리 전부를 resource-group verify로 닫는다:
#   bulk set → list → show key → update value → global bulk set →
#   delete key → global bulk delete → delete all. (DTO: Tag{key,value*},
#   TagSetRequest{tags[Tag]}, TagsSetRequest/TagDeleteRequest{tags: {srn: [...]}}.)
# components-주소 per-key 3종(show/update/delete by region/service/type/id/key)은
# components 주소 스킴 확정 후 2차 (updatecomponentstags(bulk)는 검증됨).
#
# 2026-06-15 docs-mapper enrichment (notes/comments ONLY — no shape change).
# Userguide cited:
#   [U1] /userguide/management/resource_groups/overview/
#   [U2] /userguide/management/resource_groups/how_to_guides/
# [U2] Resource Group console create requires: 그룹명(name), 자원 유형(resource
#   type — 전체 or multi-select), 그룹핑 기준 태그(grouping tags, key+value).
#   Optional: 설명(description), Lock(잠금 여부), Init Script(≤45,000 bytes),
#   그룹 자체 태그. This confirms the existing node note: the verified API create
#   needs only name+description, and resource_types/grouping-tags land via the
#   PUT-set verify step (console front-loads them; API splits them). UNPROVEN
#   whether the API enforces the grouping-tags-required rule that the console does.
# [U2] 태그는 "자원 당 최대 50개까지 추가 가능" — max 50 tags per resource
#   (confirms the prior _note; LOCK candidate).
# [U2/U1] STILL UNSPECIFIED in userguide+overview: resource-group name

version: 1
resources:
  resource-group:
    code: "mg-rm-resource-group"
    service: management/resourcemanager
    requires: []
    create:
      endpoint: "POST /v1/resource-groups"
      body: {name: "regr-rg-{unique}", description: "created by API regression suite"}
    # rg_srn: 소스 lifecycle이 capture_soft하던 envelope — 하드 승격 (owner
    # 2026-06-13: 자원 생성 시 srn 발급). 비면 capture-failure 본문이 정답을 줌.
    capture: {rg_id: "$.resource_group.id", rg_srn: "$.resource_group.srn"}
    verify:
      - {name: read-resources,
         endpoint: "GET /v1/resource-groups/{rg_id}/resources",
         expect_status: [200]}
      - {name: set,
         endpoint: "PUT /v1/resource-groups/{rg_id}",
         json: {name: "regr-rg-{unique}", description: "updated by API regression suite",
                resource_types: ["resourcemanager:resource-group"],
                tags: [{key: "regrset{unique}", value: regrv}]},
         expect_status: [200, 202],
         note: "set은 tags 비어있으면 400 'tags must not be empty' (run 27452095757) — 비어있지 않은 태그 필수"}
      - {name: show-resource,
         endpoint: "GET /v1/resources/{rg_srn}",
         expect_status: [200, 403],
         note: "PF-18 — GET /v1/resources/{srn} 403 'Forbidden / You do not have permission to Action' (run 27466988779). 5th missing-action-definition case (cf. PF-01/PF-15) — product gap, not our body. [200,403] 허용으로 통과시키고 액션 정의가 추가되면 strict 200으로 조임."}
      - {name: tags-bulk-set,
         endpoint: "PUT /v1/tags/{rg_srn}/bulk",
         json: {tags: [{key: "regr{unique}", value: regrv}]},
         expect_status: [200, 201, 202]}
      - {name: tags-list,
         endpoint: "GET /v1/tags/{rg_srn}",
         expect_status: [200]}
      - {name: tag-show,
         endpoint: "GET /v1/tags/{rg_srn}/regr{unique}",
         expect_status: [200]}
      - {name: tag-update-value,
         endpoint: "PUT /v1/tags/{rg_srn}/regr{unique}",
         json: {value: regrv2},
         expect_status: [200, 201, 202],
         note: "TagValue DTO는 {value} 단일 필드"}
      - {name: tags-global-bulk-set,
         endpoint: "PUT /v1/tags/bulk",
         json: {tags: {"{rg_srn}": [{key: "regrx{unique}", value: regrv}]}},
         expect_status: [200, 201, 202],
         note: "TagsSetRequest: {srn: [Tag]} 맵 — dict KEY 자리의 placeholder는 엔진 _fill_obj가 키도 치환하는지 라이브로 확인 (실패 시 본문이 알려줌)"}
      - {name: tag-delete-one,
         endpoint: "DELETE /v1/tags/{rg_srn}/regr{unique}",
         expect_status: [200, 202, 204]}
      - {name: tags-global-bulk-delete,
         endpoint: "DELETE /v1/tags",
         json: {tags: {"{rg_srn}": ["regrx{unique}"]}},
         expect_status: [200, 202, 204],
         note: "TagDeleteRequest: {srn: [key,...]} 맵"}
      - {name: tags-delete-all,
         endpoint: "DELETE /v1/tags/{rg_srn}",
         expect_status: [200, 202, 204]}
    delete: {endpoint: "DELETE /v1/resource-groups/{rg_id}", destructive: true}
    provenance: VALIDATED
    source: {lifecycle: resourcemanager-resource-group, steps: [create, delete]}
    notes: "글로벌(account-scoped) 서비스 — host에 region 세그먼트 없음. 싸고 가역적인 실생성 자원 — tag-write 계열의 실 SRN 공급원 (owner 2026-06-13 계획). rg_srn envelope은 소스 capture_soft에서 하드 승격 — 1차 라이브에서 확정. 콘솔 생성은 name(필수)·description(선택)·resource_types(필수)·그룹핑 기준 태그(필수) 요구 — 검증된 API create 는 name+description 만으로 201, resource_types/tags 는 PUT set 에서 적용(verify set 노드). 삭제는 영구(복구 불가) — destructive 표시와 일치."
    _note: "docs(how_to_guides 2026-06-14, 재확인 2026-06-15 [U2]): 태그는 자원당 최대 50개('자원 당 최대 50개까지 추가 가능'). 콘솔 create 필수=그룹명+자원유형(전체/멀티선택)+그룹핑 기준 태그(key/value); 선택=설명·Lock·Init Script(≤45,000 bytes). resource-group 이름 길이/허용문자 및 계정당 그룹 최대 개수는 overview+how_to_guides 양쪽 모두 미명시(2026-06-15 재확인, API Reference 미확인) — quota/naming 미상, 라이브에서 확정 필요. PROBE-READS gap_getid (B-rows, NOT wired — noted not invented): the 4-segment component-addressed reads GET /v1/resources/{region}/{service}/{resource_type}/{resource_identifier} + GET /v1/tags/{region}/{service}/{resource_type}/{resource_identifier} + .../{key} CANNOT be wired off this VALIDATED node. This create captures only rg_id ($.resource_group.id) and rg_srn ($.resource_group.srn); validate.py L819-864 requires every verify-read token to resolve to this node's OWN capture/builtin. The (region/service/resource_type/resource_identifier) tuple + tag {key} are NOT in the create response — resourcemanager-tag-lifecycle obtains them only via a SEPARATE GET /v1/resources?limit=1 discover-resource-addressing step (capture_soft $.contents[0].region/service/resource_type/resource_identifier/tags[0].key, explicitly BEST-GUESS + UNPROVEN). Injecting those soft captures here would be inventing an unproven capture path on a VALIDATED parent — forbidden by the probe-read guardrail. The SRN-COMPOSITE siblings ARE already wired off the cleanly-captured rg_srn: show-resource (GET /v1/resources/{rg_srn}), tags-list (GET /v1/tags/{rg_srn}), tag-show (GET /v1/tags/{rg_srn}/regr{unique}) — distinct catalog keys from the 4-segment forms. Closing the 3 component-addressed endpoints needs the discovery tuple live-proven first (promote $.contents[0].* in resourcemanager-tag-lifecycle from capture_soft to a hard capture), then a tuple-capturing lookup/sibling node can carry the verify."
